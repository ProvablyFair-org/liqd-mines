## Game and algorithm

The board is always **25 tiles** (a 5×5 grid), numbered `1 … 25` across rows: tile 1 is the top-left square, tiles 1–5 the top row left to right, tile 25 the bottom-right square (evidence E22). Before the round the player selects `mineCount`, an integer in `[1, 24]`; that many tiles are mines and the rest are safe. Each revealed safe tile raises the multiplier, revealing a mine ends the round with payout 0, and the player may cash out after any number of safe reveals. There are no risk levels and no variants: `mineCount` alone determines the odds and the multiplier schedule, so there are 24 configurations, and with `1 ≤ k ≤ 25 − m` safe reveals, **300 legal (m, k) cells**. A `GONGA_MINE` `gameId` appears in the client bundle but is an unbuilt placeholder with no live surface, and is out of scope.

```
commit    = SHA-256( UTF-8(serverSeed) )                     // over the 32 hex characters, not the 16 bytes
key       = hex_decode(serverSeed)                            // 16 bytes
digest(i) = HMAC-SHA256(key, UTF-8(clientSeed + ":" + nonce + ":" + i))   // one digest per draw, i = 0, 1, …

draw(i, r):                                                   // an offset in [0, r)
    LIMIT = floor(2^32 / r) * r
    for each 4-byte chunk of digest(i), big-endian, offsets 0, 4, …, 28:
        if chunk < LIMIT: return chunk mod r                  // the rejection test is ASSUMED of the operator, unexercised
    (all eight rejected: not specified, docs/ALGORITHM.md O1)

a = [1, 2, …, 25]
for i in 0 … mineCount−1:                                     // draws past mineCount cannot change a[0 … mineCount−1]
    j = i + draw(i, 25 − i)
    swap a[i], a[j]
mineTiles  = a[0 … mineCount−1]                               // draw order

paidMult   = win:  (1 - houseEdge) * Π_{i=0}^{k-1} (25-i)/(25-mineCount-i)   // EXACT, credited to winningAmount
             loss: 0
dispMult   = floor2( paidMult )                               // the `multiplier` field — DISPLAY only, cosmetic
```

`houseEdge = 0.01`. The commitment hashes the UTF-8 text of the 32-character hex seed; the HMAC key is the 16 hex-decoded bytes (`commitHash` and `generateProvablyFairNumber` in `src/rng.ts`). The message is `clientSeed`, `nonce` and `cursor` joined by literal colons, no zero-padding; the cursor is the draw index `i`, one fresh HMAC per swap. This is [docs/ALGORITHM.md](docs/ALGORITHM.md) §1–§3, where each step names its source (LIQD's public pages, the standard construction, or the live rounds); `src/rng.ts` runs the shuffle over all 25 positions, which leaves the first `mineCount` unchanged. The returned mine list is order-sensitive and `mineTiles` is checked with an ordered array comparison. Because the first `mineCount` shuffled tiles are the mines, a single shuffle serves every mine count under the same inputs, and the player's reveal positions are not inputs to `revealMines`. With independent uniform accepted draws the construction gives the uniform layout model used in the probability calculation. There is no external entropy (no drand, block hash or VRF): pure server seed, client seed and nonce, the same shape as LIQD Plinko. **All 6,900 captured layouts match this implementation**, 0 mismatches, 0 skipped; **138 of 138** revealed seeds match their commitments and **137 of 137** next-seed links hold, plus the pre-capture link into the first captured epoch.

**The rejection branch is ASSUMED as operator behaviour (DL-3).** The per-draw rejection probability is `(2³² mod range)/2³²`, at most **4.889e-9** (at `range = 25`) and **1.173e-9** averaged over the 25 ranges a shuffle uses, so the expected number of rejection events across the capture's **172,500 draws is 2.024e-4** — about a **0.02%** chance a capture this size ever witnesses one. The census was executed: **0 observed** (`outputs/audit-figures.json` → `moduloBiasRejectionCensus`). A no-rejection implementation reproduces all 6,900 layouts identically; if the branch were absent the residual bias would be ≤4.889e-9 per draw. The Pass-1 simulation does exercise it in the auditor's implementation — serverSeed `1f1da0da5907129a0043f5ac8a12b5ee`, clientSeed `097bf01483879668f626781b35b297c2`, nonce 760455, cursor 12, range 13: the first chunk 4294967288 is rejected at the threshold 4294967287 and the second, 412214211, yields 6 where deleting the branch would yield 1. Cursor 12 is past the first 5 tiles of that m=5 row, so the mine layout is unchanged either way while the full 25-tile permutation is not. That vector is a unit test (`tests/mines/qaRegressionTests.ts`) and, since 2026-09-23, part of Step 5, which prints `maxFair` for all 25 ranges and requires the auditor's draw to be exactly unbiased (mutation M12 now FAILs Step 5). It settles the branch in the auditor's code only, never in the operator's. *(Corrected 2026-09-10, QA-12: the documents previously said none of the 24,000,000 simulated rounds took the branch.)*

**Where the RNG code comes from.** `src/rng.ts` was rebuilt on 20 October 2026 from the written specification [docs/ALGORITHM.md](docs/ALGORITHM.md) (a copy of the framework's `games/liqd-mines/ALGORITHM.md`; the module was rebuilt from its revision SHA-256 `3576d1ea…baf2231`, and the copy here is the 21 October 2026 revision `72628054…a9fd4f5`, which only closes O5, the tile numbering on the grid) by an implementer who read only that specification and a list of export names and types, and never opened LIQD's code, its client bundle or the earlier `src/rng.ts`. The specification itself was written without LIQD's code (its §8 lists every file read). LIQD's code is a second check, not the source: its three validation vectors run as unit tests (`tests/mines/rngTests.ts`). Measured on integration, over every round in `data/` (8,900 rounds, three captures, seeds paired to rounds by hashing): the rebuilt module matches the live `mineTiles` in recorded order on 8,900 of 8,900 and the commitments on 178 of 178 seed records; LIQD's mine-placement code as given in its private specification, run outside this package, on 8,900 of 8,900; the ProvablyFair.org site verifier on 8,900 of 8,900. On inputs no captured round reaches they differ: when all eight chunks of a digest are rejected (below 1e-66 per draw) the rebuilt module throws where LIQD's code redraws at `cursor + 1,000,000`, and the rebuilt module throws on a mine count outside 1–24, a server seed that is not even-length hex, or a negative or non-integer nonce, where LIQD's code returns a layout. Until 20 October 2026 `src/rng.ts` was the auditor's reconstruction from LIQD's client bundle, checked against that private specification. The audit's draw-bias bound is `src/bias.ts` and the simulation's seed derivation `src/seed-derivation.ts`, both moved unchanged out of the old module.

## Payouts and RTP

Let `m` be the mine count and `k` the number of safe tiles revealed before settlement. For uniform mine placement:

```text
P(win at depth k) = C(25-m, k) / C(25, k)
                 = product over i=0..k-1 of (25-m-i)/(25-i)

exactMultiplier  = (99/100) × product over i=0..k-1 of (25-i)/(25-m-i)

theoreticalRTP   = P(win) × exactMultiplier
                 = 99/100

winningAmount    = floor(stake × exactMultiplier × 10^8) / 10^8
displayMultiplier = floor(exactMultiplier × 100) / 100
```

Each factor cancels, establishing **99.0000% theoretical RTP** and a **1.00% theoretical house edge** across the entire legal grid. This identity concerns the uncapped reference formula before settlement rounding; it does not establish cap enforcement or operator-side settlement at configurations absent from the capture. Win probabilities come from independent combinatorics, never operator data (Step 13 adds an exhaustive integer tally). There is no multiplier table file: the multiplier is a closed-form function of `(mineCount, tilesRevealed)`, so only the dataset is pinned. `src/config.ts` provides `minesMultiplierExact`, `minesMultiplier`, `winProbability`, `pairCoOccurProb` and `theoreticalRTP`.

**Settlement (audited dataset).** All **3,104 wins** credit `floor8(stake × exact)` in `winningAmount` (Step 8, exact BigInt arithmetic, 0 tolerance; the residual against the unrounded value is at most **8.571e-9**, gated at 2e-8), and all **3,796 losses** report zero. 1,214 wins sit a hair below the unrounded value, never above: total shortfall **$5.868e-6 on $2,670.00 staked (2.2e-9 of turnover)**. The same rule holds at both captured stakes, $0.10 and $10.00. Winning settlements cover **25 configurations**: `(m,1)` for all 24 mine counts and `(3,5)`. The displayed `multiplier` equals `floor2(exact)` on 3,104 of 3,104 wins (Step 7) and is absent on losses; on 2,662 wins it sits below the credited multiplier (player-favourable, cosmetic), never above. ### Simulation

**Pass 1** (`outputs/simulation-results.json → pass1_fresh_seeds`) records **24 configurations × 1,000,000 rounds = 24,000,000 rounds** of the auditor's implementation; every row stores its server and client seeds. Mine placement is a constrained multinomial (exactly `m` mines among 25 tiles), so a naive per-tile chi-squared with `df = 24` applies the wrong null (its fair-null expectation is `25 − m`) and is extremely conservative at high mine counts, though it still rejects gross biases (a reviewer's counterexample at m = 24, N = 1e6 gives a naive χ² of 156.25 on df 24, p ≈ 2e-21). Pass 1 therefore scores three properties at the Bonferroni threshold α/24 = 4.167e-4:

| Scored check | Coverage | Result |
|---|---|---|
| First-drawn tile uniformity (`df = 24` correct: one outcome per round) | 24 mine counts | 0/24 uncorrected, 0/24 Bonferroni |
| Pairwise mine co-occurrence vs `N × C(23, m−2)/C(25, m)`, max \|z\| over 300 binomial-standardized pairs | 23 mine counts (m ≥ 2) | 0/23 Bonferroni; largest \|z\| 3.72 |
| First-drawn-tile serial independence (lag-1 + runs on `revealMines(...)[0]`) | 24 mine counts | 1/24 uncorrected, 0/24 Bonferroni |

The pair test uses a normal approximation to a discrete binomial count (`X ~ Binomial(N,q)`, `q = m(m-1)/(25×24)`), not an exact finite-sample law. The serial statistic consumes only the first drawn tile of each round, so it is not a layout-level claim (DL-8); the one uncorrected trip is mine count 15 on its lag-1 arm (|r₁z| = 2.32 against 1.96), the runs arm is clear everywhere (minimum p = 0.0715), and ≈1.4 trips across 24 configs are expected by chance. Mean simulated RTP is **98.94271044%** (98.9427%), the unweighted mean of the 24 per-configuration estimates, approximately **1.66 modeled standard errors below 99.0000%** (pooled SE ≈0.0346 pp; z = −1.655); the worst config for the `simRTP` 5·SE band is m = 23 at 2.38·SE. The convergence chart plots the pooled single-tile RTP at seven cumulative sample sizes against 99.0000% with a ±2 × SE band (SE = σ/√n) narrowing from ±2.22 pp at 1K to ±0.069 pp at 1M; the final interval [98.8736%, 99.0118%] contains the theoretical value. Across five independent 24M-round runs on record (the committed one plus four from external reviewers), the reviewers observed a spread of run means slightly wider than the nominal pooled SE (their figure: Σz² = 12.8 on 5 df, p ≈ 0.03); it is weak evidence, consistent with noise at five runs, and not a gate. The 24M-round simulation confirms RTP at `k = 1` only. These results establish that the specified finite tests passed; they do not establish the absence of every form of dependence or bias. Since 2026-09-24 every verify run replays all 24,000,000 rounds from each row's seed pair (Step 16: 0 census mismatches, 0 derived statistics beyond tolerance).

**Pass 2** evaluates each of the **138 revealed server seeds** over **10,000 nonces**: early window 0–49, late window 50–9,999 (locally generated extensions, not observed bets). The statistic is the first-drawn tile histogram. `chiSquaredTest` in `src/stats.ts` pools **inward from the two ends only** while the end cell's expected count is below 5; interior cells are never pooled. At 50 draws the expected vector is `[6, 2×19, 6]`: a **21-cell statistic on 20 degrees of freedom**, with nineteen interior cells at expected 2. The late window keeps all 25 cells (expected 398) and `df = 24`. Result: **4 flagged seeds** against **6.555** under the nominal model `Binomial(138, 0.05 × 0.95)`; binomial survival probability **0.89757317** (0.8976); Step 17 passes. ## Reproduce the audit

Runtime: **Node 22.x** (`package.json` `engines` and `.nvmrc`); the committed artifacts were produced on that line, and a derived statistic's last bits are runtime-dependent. The lockfile lists Mocha 11.7.6, ts-node 10.9.2, TypeScript 5.9.3, `@types/node` 22.20.1 and `@types/mocha` 10.0.10.

`npm test` is `node scripts/run-stages.mjs test`: four stages, each run whatever the previous ones returned. `scripts/check-standalone.mjs` re-hashes every TypeScript source, the tsconfig, the lockfile and the build scripts against `standalone-manifest.json`, fails if the bundled `test.js` / `verify.js` and the sources disagree by a byte, and checks that the audit ID and the counts quoted in the Markdown at the package root equal the registries; `node test.js` runs the **49 bundled unit tests**; `node verify.js` runs the **22 scored verification checks**, including the full Pass-1 replay and complete Pass-2 bootstrap reconstruction; `node scripts/release-manifest.mjs --check` checks the release manifest and the release bar. `npm test` exits with the verifier's code when the other three pass, and 1 when one does not. **The reproduction gate.** `npm run verify` compares what it computed against the committed artifacts field by field and writes `outputs/run/verification-results.json`, `outputs/run/audit-figures.json` and `outputs/run/diff.json`, with the runtime. ## Verify a bet

The steps below use the field names of this audit's dataset (`data/mines-master-6900bets.json`). They need Node.js and nothing else.

1. **Where the seed is revealed.** Before you play, LIQD's provably-fair **Seeds** panel shows the **Active Server Seed (Hashed)** — the commitment, `hashedServerSeed` — beside your **Active Client Seed**, and under **Rotate Seed Pair** the next pair: a **Next Client Seed** you can replace with your own (**CHANGE**) and the **Next Server Seed** hash (evidence E12, E13). The server seed itself stays secret while you play under it. Rotating the pair makes the next pair active and reveals the retiring server seed in plaintext: all 138 retired seeds in this capture were revealed that way, recorded from the response to the rotate request (`capture/capture-mines.reference.mjs`). The Seeds panel itself does not display the revealed seed (E12); it is shown under **My Bets**: open a round played under the retired pair and expand **Provably Fair**, which lists that round's Client Seed, Server Seed, Nonce and Mines (E21). Rotate first, then verify rounds from the retired pair. **Before you rotate, copy the Active Server Seed (Hashed) from the Seeds panel** (the label as shown in E13): the round view does not show it (E21), and after rotation the Seeds panel shows the next pair's hash in its place (E12).
2. **Which fields to take.** From the round's **Provably Fair** section under **My Bets** (E21), which lists four values: Client Seed (`clientSeed`), Server Seed (`serverSeed`, once the pair is rotated), Nonce (`nonce`, 0 for the first round after a rotation, counting up) and Mines (`mineCount`). From the Seeds panel before rotating: Active Server Seed (Hashed) (`hashedServerSeed`, step 1). From your own board: the tiles you opened, in order (`openTiles`), and where the mines were (`mineTiles`), numbered as in step 5.
3. **Check the commitment.** `SHA-256` of the `serverSeed` hex **string** as UTF-8 text — not of the 16 bytes it decodes to — must equal `hashedServerSeed`.
4. **Recompute the shuffle** ([docs/ALGORITHM.md](docs/ALGORITHM.md) §2). The HMAC key is the hex-decoded `serverSeed`. For each draw `i` = 0 … `mineCount` − 1, with `r` = 25 − `i`: take `HMAC-SHA256(key, "clientSeed:nonce:i")`, read it as eight 4-byte big-endian integers, and use the first one below `LIMIT = floor(2^32 / r) × r` (this rejection step is ASSUMED of LIQD's server, unexercised by any captured round); the draw is that integer mod `r`. Swap position `i` with position `i + draw` in the list 1 … 25 (a forward Fisher-Yates shuffle). Draws past `mineCount` cannot change the first `mineCount` positions.
5. **Read the result.** Tiles are numbered **1 to 25** across rows: tile 1 is the top-left square, tiles 1–5 are the top row from left to right, 6–10 the second row, and so on to tile 25 at bottom right; tile `t` is in row ⌈`t`/5⌉, column ((`t` − 1) mod 5) + 1. Evidence E22: the finished board of the E21 round, whose seed computes mines [12, 1, 25], shows its three mines at top-left (1), row 3 column 2 (12) and bottom-right (25); numbering down columns would put tile 12 at row 2 column 3. E22 alone would also fit a "snake" order (rows alternating direction); LIQD's own Verify-tab picture of its nonce-7 test case (held on file, not published) shows mines [3, 17, 16], which this package's `src/rng.ts` computes for that case, at row 1 column 3, row 4 column 2 and row 4 column 1, as plain across-rows numbering places them (a snake order would put 17 and 16 at row 4 columns 4 and 5). The first `mineCount` tiles of the shuffled list are the mines, in draw order, and must equal `mineTiles`. A round is a win exactly when none of your `openTiles` is a mine; a losing round ends on the first mine you opened. A win pays `floor8(stake × exact multiplier)` ([Payouts and RTP](#payouts-and-rtp)).

The same calculation as a script, filled in with a round from this dataset (bet `GbqOuPvhQekqcARNtHZ3_`, whose recorded `mineTiles` are `[6, 20, 7]`) — replace the five values with your own:

```js
// save as check-round.mjs and run: node check-round.mjs
import { createHash, createHmac } from 'node:crypto';
const serverSeed = '8b2fc7e909d2fff439692f648a9df0ba';   // revealed after rotation
const hashedServerSeed = '5d6c4f105f182f9798063a4ca29d2c4ad2c575449bc5742a9680ec31bd9d79a0';
const clientSeed = 'audit59c2b0bf86aa', nonce = 25, mineCount = 3;

// docs/ALGORITHM.md §1.2: SHA-256 over the seed's characters, not the bytes they encode
console.log('commitment ok:', createHash('sha256').update(serverSeed, 'utf8').digest('hex') === hashedServerSeed);
// §2 steps 1-2: one HMAC per draw i, first big-endian 4-byte chunk below LIMIT, mod r
function draw(i, r) {
  const d = createHmac('sha256', Buffer.from(serverSeed, 'hex')).update(`${clientSeed}:${nonce}:${i}`).digest();
  const LIMIT = Math.floor(2 ** 32 / r) * r;   // rejection: ASSUMED of LIQD's server, unexercised by the capture
  for (let o = 0; o < 32; o += 4) { const v = d.readUInt32BE(o); if (v < LIMIT) return v % r; }
  throw new Error('all 8 chunks rejected: not specified (docs/ALGORITHM.md O1)');
}
// §2 step 3: forward Fisher-Yates over tiles 1..25; the mines are the first mineCount, in draw order
const a = Array.from({ length: 25 }, (_, t) => t + 1);
for (let i = 0; i < mineCount; i++) { const j = i + draw(i, 25 - i); [a[i], a[j]] = [a[j], a[i]]; }
console.log('mines:', a.slice(0, mineCount));   // [ 6, 20, 7 ]
```

For bet `GbqOuPvhQekqcARNtHZ3_`, the first HMAC message is `audit59c2b0bf86aa:25:0`; with seed A decoded as hex bytes the digest is `c9868d2c53d8031cc5718fa68613ac548d4c37fb5c296654abc9782f640be138`. Its first four bytes are `3381038380`, below `maxFair = 4294967275` for range 25; the remainder is 5, so the first swap puts tile 6 in the first mine position. Opened tile 2 is safe; the probability is `22/25`, the exact multiplier `(99/100) × (25/22) = 9/8`, and the payout `floor8(0.10 × 9/8) = 0.11250000`.

## Limitations and trust

**Excluded:** infrastructure, server and platform security; wallet balance reconciliation, payment processing, custody and account systems beyond the recorded game-settlement responses; enforcement of maximum-profit, maximum-odds and other payout limits; uncaptured game paths (mid-round seed rotation, and interactive cash-out beyond the scored supplement's 1,000 rounds); public-production behaviour and behaviour outside the captured sample; promotional, bonus and loyalty programs; responsible-gambling features; other games on the platform; the server's entropy source (bounded by the commitment, not measured). The capture is one account in one collection window; LIQD is a centralized platform with no on-chain record, and verifiability rests on the commit-reveal scheme. The statistical findings concern the specified tests of the auditor's implementation and captured seed inputs; they do not establish universal backend independence or the absence of adversarial seed selection. Live-bet RTP is a variance illustration, never RTP evidence. These are boundaries of the evidence, not observed operator faults.

### Operator trust

LIQD Mines uses the **Client Seed + Server Seed** model: the server seed is secret until reveal and not player-controllable; its commitment is observable before any round; the client seed is observable and player-editable; the nonce is LIQD state, controllable only via ordering. What commit-reveal proves on this dataset: no post-bet change of layout on the recorded order (Steps 1, 2, 5), truthful reveal (138/138), client-seed consumption, faithful execution (6,900/6,900) and payout conformance (3,104 wins, 3,796 losses; 393 supplement wins). What it does not prove:

- **R-CHERRY — server-seed cherry-picking.** Containment: **STRUCTURAL (medium)**. The primary defence is the client-seed-after-commitment mitigation: a player who sets or rotates their own client seed after seeing the commitment removes the operator's foreknowledge channel. **Caveat on the Phase D demonstration:** the auditor's Phase D client seeds were `pfaudit-<fixed-stamp>-<epoch>`, i.e. `pfaudit-1785428583504-120 … -129`. **All ten Phase D epochs, 120–129 — 500 bets, $50.00000000 wagered, $51.58368132 credited (player-favourable, no adverse signal) — used that form**, so foreknowledge-denial holds by construction for 128 of the 138 epochs and the other 10 rest on the recompute (Step 5) and the clean Pass-1/Pass-2 statistics (Steps 16/17). *(Correction QA-06, 2026-09-10: this used to count 129 of 138, exempting epoch 120 as the first occurrence of the pattern; that reasons from position, not construction. Epoch 120's seed carries the same stamp, which decodes to 2026-07-30 16:23:03.504 UTC — 4 ms before `meta.startedAt` and 5,250.153 s before the record that commits epoch 120 (`seeds[epoch 119].at = 17:50:33.657 UTC`). These are recorded times within the capture's own chronology, and nothing here asserts that the operator predicted or exploited any seed. The old 9 / 450 / $45.00 / $47.82791825 subtotal is arithmetically correct for its subset; the subset was the wrong one. `src/figures.ts` emits the group as `phaseDTimestampPatternEpochs`. No historical bet seed was edited.)* Pass 2 is a secondary gross-bias check. Residual risk **MEDIUM — structurally contained**; an external-entropy beacon would collapse it to LOW by construction.
- **R-ORPHAN — server-side selective orphaning.** An operator observing a round's outcome and orphaning or re-issuing it is not detectable from a client-side dataset (this capture has no nonce gaps). An external-entropy beacon does not close it, and a server-side audit log the operator controls proves nothing about completeness; independently verifiable acceptance/settlement records (a tamper-evident, externally anchored append-only log, or player-signed bet acknowledgements) would. Containment: **DISCLOSED (out of scope for client-side capture).**
- **R-PAYOUT — payout-formula integrity.** Full coverage on the witnessed cells — 25 of 300 in the audited dataset (45 with the supplement); a deviation confined to an unwitnessed depth would not be caught (A1).
- **R-TRUNC — displayed-multiplier truncation (cosmetic).** The display understates the credited amount (player-favourable). Containment: **DISCLOSED.**
- **R-MULTI — multi-account seed correlation.** Cross-account seed reuse cannot be detected from a single-account dataset. **OUT OF SCOPE (disclosed).**
- **R-BRACKET — parameter boundary edge cases.** Mine-count boundaries (1 and 24) and reveal depths 1 and 5 are covered across Phases A/B/E; deeper depths are sampled only by the supplement; intermediate-state invariance is structural, not captured. The `maxOdds` boundary (above) was neither triggered nor tested. **DISCLOSED.**
- **R-CREDIT — credited-amount confirmation channel.** Payout conformance is verified against the reported `winningAmount`; no wallet balance-delta cross-check was captured (A4). **DISCLOSED.**
- **R-RACE — mid-round seed-rotation race (TOCTOU).** Not exercised; a bug class PF.org has found on another operator's Mines (A5). **OUT OF SCOPE (disclosed).**

## Terms

**Commit-reveal:** the server publishes `hashedServerSeed` before any bet and reveals the plaintext `serverSeed` after rotation. **Server seed:** a 32-character (16-byte) hex string; the HMAC key in its hex-decoded form. **Commitment:** `SHA-256(utf8(serverSeed hex string))`, the Stake convention. **Client seed:** a player-controlled string mixed into the HMAC message. **Nonce:** bet position within an epoch, 0–49. **Cursor:** the draw index `i`, the 0-indexed shuffle position (0…24). **Epoch:** 50 bets under one seed pair. **Fisher-Yates shuffle:** the in-place algorithm producing a uniformly random permutation. **`mineTiles`:** mine positions in draw order, compared as an ordered array. **`mineCount`:** mines on the grid, 1–24. **Reveal / open tile:** `reveals` is the planned count, `openTiles` the tiles actually opened. **Modulo-bias rejection:** discarding `uint32` values at or above `maxFair = floor(2³²/range)·range` before `% range`; ASSUMED of the operator here. **Exact multiplier:** the credited `(1 − houseEdge) × Π (25−i)/(25−m−i)`. **Displayed multiplier:** the `multiplier` field, floored to 2 decimals, cosmetic. **House edge:** nominal `houseEdge = 0.01` per `/system/get-game-settings`; effective 1.00%. **RTP:** `1 − houseEdge` for the uncapped reference formula. **Win probability:** `C(25−m, k) / C(25, k)`. **Anti-circularity:** theoretical expectations from independent combinatorics, never operator-supplied probabilities. **Constrained multinomial:** exactly `m` mines among 25 tiles, so per-tile counts are negatively correlated. **Chi-squared test:** p-values from the exact regularized incomplete gamma function (`src/stats.ts`). **Bonferroni correction:** per-test threshold `α / k`; for 24 configs `4.167e-4`. **Parametric bootstrap:** the Pass 2 early-window null built from 10,000 fair replicates of 50 first-draws per mine count. **Lag-1 autocorrelation / Wald-Wolfowitz runs test:** the serial checks applied per config to first-drawn tile values. **Selective orphaning:** suppressing an already-generated unfavourable round server-side (R-ORPHAN). **EC-N:** the numbered criterion of scored step N. **E##:** a numbered evidence item. **Hard fail:** a FAIL on any step, which invalidates the claim. **Phase A–E:** the five capture phases. **`winningAmount`:** the settle-response field holding the amount credited.

### Guard codes

These are the audit framework's own rules, named so a reviewer can tell which rule a given assertion exists to satisfy. Every code used anywhere in this package is defined here.

**G-BIND** — The guard requiring that every population assertion binds to source records and to `src/config.ts` constants, never to a count the artifact supplies about itself. **A row count is not an identity.** A reviewer once obtained a clean Full Pass on a sibling package by shrinking a dataset 40% and doctoring its header to agree.

**G-VALID** — The guard forbidding rejection of the merely surprising. A statistic landing exactly on its expectation is legal. Nothing in this suite treats exactness, a zero deviation or a round number as evidence of fabrication.

**G-NONVACUOUS** — The guard requiring that a predicate cannot pass by being undefined. Every field a comparison reads is checked finite first, because `NaN` silently satisfies every `>` and `<` it appears in — a test that cannot fail is not a test.

**G-PRODUCING** — The guard requiring every quantitative claim in the report to be EMITTED by a committed pipeline step and copied from its artifact, never typed. `verification-results.json` does not satisfy this on its own: its `detail` fields are hand-authored strings, so a number interpolated into a step label traces only to itself. `outputs/audit-figures.json` is the answer — bare numbers computed from `src/config.ts`, the pinned dataset and the simulation artifact.

**G-SIMDERIVE** — The guard requiring a simulation step to recompute its predicate from the artifact's DETAIL ROWS rather than from the summary scalars it also carries. On its own it is not sufficient — it says nothing about where the rows came from — so the steps that apply it also inventory every leaf key path in the artifact and classify it ATTESTED / BOUND / BOUNDED / UNATTESTED.

**G-ROUNDING** — The audit methodology's rounding guard: credit rounding that is house-favourable and not published by the operator is a FAIL. In this package it bears only on DL-14's dated history: whether it applies to the 2026-09-26 capture's 1e-8 short credits is part of open ruling 2 (MANIFEST → Open rulings); it was not applied to Step 22 while that capture was scored, and applying it would have made Step 22 a FAIL. On the scored 2026-10-03 capture no credit is short, and a short credit there FAILs Step 22 through its zero-gap declaration whatever the guard says.

**G-WITNESS** — The guard requiring that a check state what its evidence can and cannot witness. `nonceStart`/`nonceEnd` are the CAPTURE's record of the window it served, not an operator-side counter, so asserting against them proves the bet rows agree with the capture's declared window — not that the operator served no other nonce under that seed. The limit is scored and disclosed, not assumed away.
